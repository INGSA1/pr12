# Анализ ситуации: потеря изменений при параллельной работе

## Описание ситуации

Два разработчика одновременно изменили один объект конфигурации — форму документа «Заказ». Изменения одного из них оказались потеряны (перезаписаны), а тестировщик проверял устаревшую сборку, поэтому результаты тестирования не соответствуют актуальному состоянию системы.

## Причины

1. **Нет контроля параллельной работы:** оба разработчика редактировали один объект без блокировки (захвата) или без слияния версий, последний сохранивший затёр правки первого.
2. **Работа вне репозитория / в общей копии:** изменения вносились в общую базу или локальные копии без регулярной синхронизации (`pull` / обновление из хранилища).
3. **Нет распределения задач:** задачи не были разведены по объектам, никто не знал, что форму правит второй человек.
4. **Нет регламента коммитов и ветвления:** крупные редкие коммиты, правки напрямую в основную ветку, без запроса на слияние и ревью.
5. **Не определена версия для тестирования:** сборка не привязана к коммиту / тегу, тестировщик не мог проверить, какая версия ему передана.
6. **Нет автоматической сборки и уведомлений:** тестировщик не информируется о появлении новой сборки.

## Регламент работы с репозиторием

1. **Ветки.** `main` — стабильная версия, прямые коммиты запрещены (защищённая ветка). Для каждой задачи — отдельная ветка `feature/<номер-задачи>-<кратко>`, исправления — `fix/...`.
2. **Задачи.** Один объект конфигурации — один ответственный в один момент времени; назначение фиксируется в трекере задач. Для 1С — обязательный «захват» объекта в хранилище.
3. **Синхронизация.** Перед началом работы и перед отправкой — `git pull --rebase origin main` (в 1С — «Обновить конфигурацию из хранилища»). Ветки живут не дольше 1–2 дней.
4. **Коммиты.** Небольшие, атомарные, с осмысленным сообщением («Добавить поле "Срок поставки" в форму Заказ»), ссылка на номер задачи.
5. **Слияние.** Только через merge request с обязательным ревью второго участника и успешной проверкой (сборка, автотесты).
6. **Версии и сборки.** Передача на тестирование — только из помеченного тега (`v1.2.0-rc1`); в заявке на тест указываются тег и хеш коммита. Тестировщик проверяет соответствие версии перед началом.
7. **Уведомления.** Появление новой сборки автоматически сообщается тестировщику (CI или сообщение в трекере); устаревшие сборки помечаются недействительными.
8. **Резервное копирование.** Регулярные бэкапы репозитория, права на запись — по ролям.

## Процедура разрешения конфликта

1. **Остановить работу над объектом** и сообщить команде о конфликте; зафиксировать, какие версии и чьи правки затронуты.
2. **Восстановить обе версии:** найти потерянные изменения в истории (`git log`, `git reflog`, версии хранилища 1С); сохранить копии версий.
3. **Получить актуальную базу:** `git fetch`, затем `git merge origin/main` (или `rebase`); в 1С — сравнение и объединение конфигураций.
4. **Разрешить конфликты:** открыть файлы с маркерами `<<<<<<<`, `=======`, `>>>>>>>`; вместе с обоими авторами выбрать нужный вариант или объединить изменения; удалить маркеры.
5. **Проверить результат:** собрать проект, запустить тесты, проверить форму «Заказ» вручную.
6. **Зафиксировать:** `git add <файлы>` и `git commit` с сообщением о разрешении конфликта; отправить на ревью через merge request.
7. **Повторное тестирование:** создать тег новой сборки, передать тестировщику с указанием версии, повторить затронутые тесты.
8. **Разбор причин:** определить, какой пункт регламента не выполнен, при необходимости обновить регламент.
